# Decision log: implementing SRD Version 3.2

Every choice made while implementing the SRD that it did not settle. Per your
instruction, each takes my recommended option; all are open for your review.
**Bold** rows most need your judgement.

| # | Question | Options considered | Decision | Why |
|---|---|---|---|---|
| D-01 | Where the spike finding lives | repo root; `docs/findings/` | `docs/findings/FINDING-2026-11-20-connected-systems.md` | Findings are dated documents; keeps the root clean. |
| D-02 | Reuse of the closed V1 work (PR #2) | start from nothing; reuse what V3.2 keeps | Reused the world generator, timetable and weather model, Pyodide fetch scripts and the Service Worker pattern; rewrote everything that changed | The simulated world is unchanged by V3.2 (except no GPS); its FR-07 coverage tests still hold. |
| D-03 | Canal and timetable | — | As V1: 9 km, ten reaches, five locks, six bridges, 600 m tunnel; timetable period 5 h 45 m | Every reach is met at every hour within a week (tested for three seeds). |
| D-04 | Precipitation type (the measured extra field) | — | Generated from air-mass wetness, humidity anomaly and fronts; dry in the tunnel; stored as a one-letter code (N, D, R, S) | Gives a real Category to switch on; the coded letter adds to the store's awkwardness. |
| D-05 | Logger record without position | — | 48-byte fixed-width record: half-second ticks since 1994, METAR minus, `VRB`, `/` for missing, precipitation letter; daily files `BOW_`/`STN_`; flushes hold back 17 bytes | Keeps every FR-19 awkwardness; no position anywhere (tested). |
| D-06 | Four-week pre-generation speed (FR-16) | per-record Python; vectorised numpy | Vectorised truth, noise and fixed-width formatting | 2.4 M records per sensor in 14 s in CPython; the browser figure is in the finding. 232 MB of store. |
| D-07 | Noise must not depend on how time is chunked | one sequential stream; hour-aligned blocks | Noise drawn in hour-aligned blocks, each from the sensor's named stream keyed by block number | Found by AT-11: pausing changed readings. Now paused and unpaused runs produce identical stores. |
| D-08 | The server's index (FR-29) | parse everything into columns; per-file time index, parse on demand | Per-file array of record times; byte ranges parsed only when asked | Memory stays near the store's own size; a week of one sensor parses in well under a second. |
| D-09 | How waiting mode is made visible (FR-44) | rebuild in one go; rebuild in steps | Rebuild in steps of 200 000 records per worker tick; 503 with `Retry-After: 2` until done | Several seconds of 503s are observable at four weeks. |
| D-10 | Instance identifier (FR-45) | random UUID; seed and start count | `"{seed}-{start number}"`, sent as `ETag` on the landing page and `x-server-instance` on every reply | No unseeded randomness (FR-15). |
| D-11 | Where promoted products are kept | in the server instance; in a registry that outlives it | A registry that outlives server restarts, as a real server's database would | A server restart should not lose what scientists registered. Field toggles never touch it. |
| D-12 | Clock speeds (FR-53) | — | 0.1, 0.25, 0.5 (default), 1 and 2× | **The top rate must be measured on the target display;** 2× was judged by eye at 1920×1080 in a headless browser. |
| D-13 | Analysis service datastreams | one per SRD output; plus a runs datastream | `derived`, `changes`, `correlation`, `clusters`, plus `runs` (settings, data range and scores of each run) | FR-33 and FR-34 need settings, range and score with every result. One runs datastream, referenced by `run_id` from each output, carries them in standard SWE fields rather than invented members. |
| D-14 | When analysis runs | on every poll; on command | At server start with defaults, then on each command; derived values are computed per request | Commands are the SRD's mechanism for settings (FR-26). |
| D-15 | Command execution | asynchronous; synchronous | Synchronous: PENDING, ACCEPTED, then COMPLETED or FAILED within the request | Simple and still a real status history. |
| D-16 | Analysis parameter set in the control stream | free text; booleans | One Boolean `include_<parameter>` per published parameter, plus bounded window, clusters and sensitivity | Lets the client draw its controls from the schema alone (FR-60). |
| D-17 | Change detection without position | — | Minute-scale steps in temperature, humidity and water temperature; hour-scale steps in pressure and dew point; reported with scale and strength | Place/weather attribution is excluded in V3; the scale is reported instead. Scored against reach boundaries and fronts from the manifest. |
| D-18 | Profile identification | by datastream id; by system uniqueId + outputName + field | uniqueId + outputName + field, with SWE type and unit | Datastream ids change when schemas change (FR-46c); output names do not. |
| D-19 | Essential field for each analysis datastream | — | derived → `dew_point` (Cel); changes → `strength` (1); correlation → `matrix` (Matrix); clusters → `regime` (Category) | One concrete field per datastream so type and unit can be checked. Switching dew point's inputs off therefore degrades the derived view, as FR-32a implies. |
| D-20 | How a server "claims" the profile | landing link only; conformance entry | The profile's id in `conformsTo`, plus a `profile` link on the landing page | A claim must be checkable; an honest server drops the claim when its offering cannot meet the profile. |
| **D-21** | **Degraded mode versus a contradicted claim (FR-39, FR-41)** | — | **An honest server with an essential field off does not claim the profile, and the client starts degraded. A server that claims the profile while discovery contradicts it is rejected. The control panel has a "misconfigured server" switch to show the second case (AT-07).** | Reconciles FR-39 and FR-41, which otherwise conflict. |
| D-22 | Media types | — | Discovery `application/json`; systems also as `application/sml+json` on request; observations `application/swe+json` by default and `application/json` on request | As the SRD and spike say. |
| D-23 | Paging | cursor; offset | `limit` and `offset`, with `next` links (in `links` for JSON, a `Link` header for SWE JSON) | Simple and standard enough; `offset` is declared in the OpenAPI master. |
| D-24 | Size limit (FR-30) | — | Default page 1 000, maximum 100 000; larger is refused naming the limit and how to narrow it | "One parameter across a week" is read in seven pages. |
| D-25 | Letter for error responses | — | Any non-2xx response is **H** (plain HTTP status) | The key has no letter for exceptions; H is the closest honest label. |
| D-26 | Conformance class URIs | — | `…/ogcapi-connectedsystems-1/1.0/conf/{api-common,system,subsystem,property,create-replace-delete,sensorml}` and `…-2/1.0/conf/{api-common,datastream,controlstream,create-replace-delete,json,swecommon-json}`, plus Common and Features Core | **To be checked against the published standards (SRD §13 open question).** |
| D-27 | OpenAPI master (FR-65) | hand-written; generated by FastAPI and committed | Generated by `scripts/export_openapi.py`, committed, and a test fails if FastAPI's output drifts | The committed file is the reviewable source of truth. |
| D-28 | Links: relative or absolute | — | Absolute, built from each request's own host | Found by AT-16: OSHConnect rejects relative hrefs. Client code still carries no absolute URL (FR-04). |
| D-29 | Datastream `validTime` | omitted; open-ended `..`; concrete | `[start of data, now]` | Found by AT-16: OSHConnect requires it and cannot parse `..`. |
| D-30 | `/systems` and subsystems | list all; top level only | Top level only; bow and stern under `/systems/barge/subsystems` | Matches Connected Systems' subsystem model. |
| **D-31** | **SWE `quality` as a reference to the flag field (FR-24)** | inline quality component; `{"href": "#…_qc"}` | **`{"href": "#…_qc"}`, as FR-24 and the spike describe** | **OSHConnect 0.5.5a1 rejects it (it accepts only inline components), and the published 3.0 JSON component schemas I could reach define no `quality` property. Needs checking against clause 7.4 of the standard.** |
| D-32 | AT-16 with OSHConnect | — | `backend/independent/oshconnect_browse.py` runs in its own CI job and environment; client defects are printed and **not** counted as passes | OSHConnect lists all systems, all 7 datastreams and reads all observations; it cannot parse our Matrix (it models `elementType` as a list, the published schema has an object) or the quality reference (D-31). The CSAPI Explorer is a web tool and is not automated. |
