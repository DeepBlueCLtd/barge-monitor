Version 4.7 interfaces (implementation contract)

These are the fixed points that the Python back end, the JavaScript stand-in, the models and the front end are built against. SRD Version 4.7 (srd-barge.md) is the requirement; this file is the design that meets it. Where the two disagree, the SRD wins and this file is wrong. docs/plan-v4.7.md gives the order of work.

Changes from 4.6 (the owner's review, 2026-11-26; decisions D-220 to D-232):

  • No replay controller. Replay is the display client's own (§8). Models process each dataset on import (§10.2). The replay component, urn:x-barge:replay, its control stream, state, log, models_ready, max_rate and svc-replay are withdrawn.
  • No access gateway. Clients talk to the data server directly (§9.3). Restricted resources are listed and refused with 403, as stock OpenSensorHub does. The gateway component and §9.5 are withdrawn.
  • No Freeze. The freeze control action, the relay's hold (x-relay-hold-ok, {held}) and frozen are withdrawn.
  • Startup names its steps, and a stall says where (§13.7).
  • The opening's back-end band is two rows of five (§12).

Names in code are normative. Both back ends implement every section that says "the server", except where a section says otherwise.

1. Component identifiers

Every captured message names its sender and receiver with one of these ids (SRD §3):

id Component Zone Value-add
folder Data folder Legacy
importer CSV importer New build · back end
server Data server (OpenSensorHub; a stand-in here) Third-party libraries
models Models New build · back end ★
scilibs Scientific libraries Third-party libraries
client Display client New build · front end ★

In the adoption opening only (§12), these ids stand in for server. They are the subsystems drawn, not a count of what the data server holds (SRD FR-120):

sub-webapi, sub-registry, sub-obsstore, sub-query, sub-commands, sub-accounts, sub-permissions, sub-admin.

No message is ever captured with these ids.

The relay is not a component, and nothing is captured to or from it (FR-03). The referee is scaffolding: its traffic is captured as models ↔︎ server with the letter I.

2. Flows and letters (SRD §3.1, §5)

src → dst Letters What
importer → folder S list (the folder) or read <file>
folder → importer L the listing (name, size, modified), or the first three CSV rows and a row count
importer → server I bulk write, one message per 1,000 rows (FR-67), with rows written n/N; and each catalogue observation
server → importer K a pushed import command
client → server Q, K an HTTP request (K is a POST to /controlstreams/{id}/commands)
server → client D, P, O, H an HTTP response (H is any status ≥ 400, including 401)
server → models D, O, H, K an HTTP response; a pushed command (K)
models → server Q, O, I a request (Q); publishing (O); the referee (I)
models → scilibs, scilibs → models I a call and its result

The display client and the models talk to the server directly (4.7: no gateway). The importer is a module inside the server and runs inside the back-end worker. Their traffic is captured where §2 says, even though no HTTP is involved (FR-65: "inside the server").

Who sends a request is told to the capture by request headers:

  • x-tap-model: <model id> for a model;
  • x-tap-quiet: 1 for work the shell counts but does not draw: models registering and catching up at startup, and the silent import of Mission A;
  • x-tap-chain: <chain> from the display client.

None of these headers decides anything in the server.

  failed?: boolean;     // a request that got no answer (server down or starting)

}

4. Time

  • Replay time is absolute UTC, as written in the CSV files. Each dataset has its own span (§6). Each display client holds its own replay time and current dataset (§8). Nothing on the server holds a replay time.
  • Real time paces each client's replay clock (rate replay seconds per real second) and the drawing. The shell has no speed control (FR-78).
  • The SimClock of 4.1 is withdrawn, together with CLOCK_RATES, DEFAULT_RATE, HOP_S in simulated seconds, and simClock in the page. One hop takes HOP_MS = 900 real milliseconds; a handshake hop takes HANDSHAKE_HOP_MS = 350.
  • Rates offered: 0.1, 0.5, 1, 10, 100 (FR-86). Nothing bounds them: models do not follow replay (§10.2).
  • Freeze is withdrawn (4.7, FR-92). Pausing the client stops its polling (FR-63a); the drawing of messages already sent finishes in real time.

5. The data folder and its CSV dialect (FR-15, FR-17)

Location. At build time scripts/build_data_folder.py writes web/public/data/folder/ and .cache/data/ (for CI).

File Span (UTC) Notes
MISSION_A_20310407.csv 2031-04-07T00:00:00Z, +24 h Imported silently at startup (FR-15)
MISSION_B_20310414.csv 2031-04-14T00:00:00Z, +24 h
MISSION_B_20310414_REEXPORT.csv 2031-04-14T06:00:00Z, +24 h Overlaps B by 18 h; about 0.1 % of the readings in the overlap differ (re-calibration)
MISSION_C_20310421.csv 2031-04-21T00:00:00Z, +12 h No STN_AWS column (stern wind speed)

All four files come from one world (seed 1) generated across 21 days. Each mission is a window of it. A file's modified date is the end of its span plus 2 hours, so dates are reproducible.

The dialect is deliberately awkward (FR-17):

  • Lines 1–3 are a comment block starting #: logger id, export tool version, and #MISSION=<name>.

  • Line 4 is the header. Fields are separated by ;, and the decimal separator is a comma.

  • Column 1 is T_HS94: half-seconds since 1994-01-01T00:00:00Z, as an integer.

  • The other columns have the sensor prefix BOW_ or STN_, a code, and the unit in brackets. Values are in the units the brackets name.

    Code Field Bracketed unit, and how it is written
    AT air_temperature [dC]: tenths of a degree Celsius, integer
    RH relative_humidity [%]
    PR pressure [hPa], one decimal place, comma separator
    AWS apparent_wind_speed [kn]: knots, one decimal place
    AWD apparent_wind_direction [deg]; VRB when variable
    SR solar_irradiance [W/m2]
    WT water_temperature [dC]
    CO2 co2 [ppm], integer

  • Missing values are written -9999, or //// for text. A missing column means the field is absent from that dataset (FR-21).

  • Rows are in time order, at 1 Hz, with no blank lines. The line ending is CRLF.

Second dialect (AT-03, tests only): backend/tests/second_dialect.py writes the same data with , separators, . decimals, ISO-8601 times, °C, m/s, and missing values as empty fields. Only the importer may change to read it.

CO₂ (FR-09a). Per sensor, in ppm. The baseline is 415 ± 8 (slow drift). The engine adds load × 180 ppm, where load is 1 under way, 0.35 in a lock, and 0.05 at a wharf (World.boat(t) gives the kind of each period). The stern sits nearer the motor, so its gain is 1.25. Noise has σ 6 ppm, and there are occasional spikes. QC is computed on import, like every other field, with a range of 250–5000 ppm and a 60 ppm spike test (D-144); both back ends use these values.

7. CSV importer (FR-20 to FR-22, FR-109, FR-110)

Its system is urn:x-barge:importer. It is created at server start, under the importer's service account.

catalogue datastream. One observation per file per change of status. Fields: time, file (Text), size (Count, bytes), modified (Time), sha256 (Text), dataset (Text, empty until imported), start and end (Time, once read), records (Count), status (Category: not-imported, importing, imported, changed, superseded), pct (Count, 0–100). The latest observation for a file is its current status. Readers ask with resultTime=latest per file, or read the whole datastream and fold it.

records is 0 until the file is imported (D-197): a Count has no missing value in OpenSensorHub, which refuses both "NaN" and null there. The status says whether it counts: it is the dataset's number of rows for imported, changed and superseded (the statuses that name a dataset), and 0 for not-imported and importing. A reader never shows that 0 as a count; the display client reads it as no count at all.

import control stream. Parameters, all present on every command (FR-27):

  • action: Category, import or rescan;
  • file: Text; empty for rescan.

The receiver validates and reports:

  • REJECTED for an unknown file, or one already importing;
  • ACCEPTED, then EXECUTING with pct in message every 10 %, then COMPLETED (or FAILED).

Import:

  1. Read the file through the folder, parse the dialect (§5), and map the columns.
  2. Compute the QC flags (QARTOD range and spike checks, as in 4.1).
  3. Create the dataset's datastreams under the sensors and CO₂ analysers. This is done inside the server, under the importer's service account.
  4. Write the rows in bulk into the store.

A file whose name matches an imported one but whose size, date or sha256 differ is imported as a new dataset. The earlier one becomes superseded (FR-21a), and its datastreams stay.

At server start the importer lists the folder and publishes not-imported, imported or changed for every file. Then, once per page load only, it imports MISSION_A_…csv with x-tap-quiet (silent, FR-15). After Reset instance this silent import does not run until the page is reloaded.

Speed. The importer panel shows rows/s for the last import. In the stand-in it must beat 50,000 rows/s, so that 24 h imports in under 4 s.

8. Replay in the display client (FR-84 to FR-90, §8.6)

There is no replay on the server (4.7, D-220). Each display client keeps:

interface ReplayClock {
  dataset: string | null;   // the client's current dataset id
  start: number; end: number; // its span, Unix seconds, from the catalogue
  time: number;             // the replay time, Unix seconds, within [start, end]
  rate: 0.1 | 0.5 | 1 | 10 | 100;
  playing: boolean;
  atEnd: boolean;
}
  • Open (from the Dataset selector, FR-103) sets dataset, start and end, puts time at start, and pauses. It sends no command. If the file is not imported, the client first sends import (§7) and opens it when the catalogue says imported.
  • Play, pause, rate and seek change the clock only. While playing, time advances by rate replay seconds per real second. At end the clock pauses and sets atEnd (FR-88). Play at the end starts again from start.
  • Reading. While playing, the client polls each datastream in use once per real second for phenomenonTime up to time (FR-63). While paused it polls nothing (FR-63a). It never asks beyond time (FR-63b), even though the server holds the whole dataset and every model's results for it.
  • Results. For model outputs, the client shows the dataset's latest complete run (§10.2). While a model's latest run on the dataset is processing, the views that depend on it say "results being prepared", with the run's pct (FR-35b). It finds this generically, from the runs__{ds} datastreams it can read; it does not know the models.
  • Default. After login, the client opens Mission A, paused at its start (FR-77). Restart client returns to that (FR-85).
  • Two clients replaying the same dataset at different rates see the same results up to their own times. The server's outputs do not change (AT-70).
  • The shell mirrors the clock in the top bar and the status box. It reads and drives it in the page, through the display client; nothing about it crosses the seam.

9. The server: behaviour both stand-ins must have (FR-06c, PR-05, PR-06)

9.1 Behaving as a stock OpenSensorHub

  • Identifiers are opaque (§6).
  • Discovery of every system is GET /systems?searchMembers=true (D-193): every system, subsystems included, in either encoding (f=application/sml+json gives uniqueId; GeoJSON gives properties.uid). GET /systems alone lists the top level; /systems/{id}/subsystems lists a system's children. A listing carries no parent link; only a single system (GET /systems/{id}) links its parent. No client relies on parent links: the system tree, where one is needed, is learnt from /subsystems (D-192). GET /collections/all_systems/items answers 400, as OpenSensorHub does; /collections lists all_systems with its items link to /systems.
  • SensorML is sent as application/sml+json (D-194), to POST /systems and POST /systems/{id}/subsystems. A body sent as application/json (or without a Content-Type) is read as GeoJSON: anything but a Feature is refused with 400, as OpenSensorHub refuses it.
  • Units are UCUM codes (D-195). A datastream or control stream whose schema carries a uom.code that is not UCUM is refused with 400 (OpenSensorHub: "Invalid UCUM code").
  • Clients read a body as JSON whatever its Content-Type says (D-196). OpenSensorHub labels the landing page, /conformance and /datastreams/{id}/schema asked without f as Content-Type: auto; the bodies are JSON. The stand-ins label them application/json.
  • POST creating something that already exists (same uniqueId, or same outputName under the same system) answers 201 with the existing Location. A different schema under an existing outputName makes a new datastream, with a new id (FR-51).
  • One observation per POST. An array body is refused with 400.
  • A missing value is the string "NaN". JSON null in a Quantity is refused with 400.
  • PUT and DELETE on observations, systems and datastreams are refused with a 4xx (D-200): the stand-ins answer 405; OpenSensorHub answers 400 to PUT with an empty body. Clients rely only on a 4xx. Open (D-224): a stock OpenSensorHub deletes a system or a datastream on DELETE (204) for an account its permissions allow, and for any account on its internal endpoint (tried on 2026-11-26). FR-28a needs the delivered OpenSensorHub configured to refuse it; that is to be settled with the OpenSensorHub team (§14). The stand-ins refuse PUT, PATCH and DELETE with 405 for every account, as the configured server is expected to.
  • The format is chosen with f=application/swe+json. The Accept header is ignored: the default is application/json observation resources. Paging is by limit and offset, with no next link in SWE JSON. A limit over the maximum is not refused.
  • A refusal is an HTML page (text/html), with the status line in <title>. No client may rely on its body.
  • There is no instance identifier and no 503. While starting, and while down, the back-end worker answers nothing ({down: true}), and the relay returns a network failure. A start takes about one real second, during which connections are refused.
  • Command status is posted to /controlstreams/{csId}/status with {"command@id": "...", "statusCode": "...", "message": "..."}. Status codes: ACCEPTED, EXECUTING, COMPLETED, FAILED, REJECTED. Listed, each report also carries its own id and its reportTime (real time); readers tell reports apart by id (D-181).
  • A command's outcome is its latest status report other than PENDING (D-199, revising D-164), by reportTime, among the reports since the command was sent. When the sender's POST answers, the server stores a PENDING report for the command: in OpenSensorHub that is often after the receiver's COMPLETED, so the latest report alone would read PENDING. Both stand-ins store it too. The display client, both csmodels (outcome, commandOutcome), the shell and the suite read it this way.
  • Sending a command: POST /controlstreams/{csId}/commands with {"parameters": {...}}. Commands go to the importer (import) and to the models; there is no replay control stream (4.7).
    • With no subscriber, the command is dropped and not listed afterwards. The answer is 202 after the hold: 5 s in the stand-ins, about 29.5 s in OpenSensorHub 2.0.4 (AT-32 run of 2026-11-26). The stand-ins keep 5 s; no client waits on either.
    • With a subscriber, the command is pushed at once. The answer is 200 after about 5 s, with currentStatus: PENDING (FR-27), and the PENDING report is stored then. The sender never waits for this answer: it does not await the response before updating its display (AT-39).
  • The profile is at GET /profile.json, beside the API (FR-41). It is not linked from the landing page.

9.2 Push subscriptions (FR-02a)

Subscribing. GET /controlstreams/{csId}/commands?subscribe=1, with the Authorization header. The answer is 200 with content-type: application/x-ndjson and a body that never ends: one command JSON per line, as {"id", "parameters", "issueTime", "sender"?}.

  • sender is the sending user's id, as OpenSensorHub puts it on a pushed command (D-152).
  • The subscription ends when the server stops, restarts or goes down. The receiver then resubscribes once the server answers again (FR-48, AT-38).

PushChannel (web/src/push.ts, and csmodel.py's subscribe) wraps this in an interface shaped like WebSocket: onopen, onmessage({data}), onclose, close().

  • Where receivers subscribe (D-223). With access control on, OpenSensorHub closes every command subscription on its public endpoint at once (S-AUTH). Receivers (the importer and the models) are server-side processes in a developed system, so they subscribe on the server's internal endpoint, which has access control off and is not reachable from outside: /api-internal beside /api. The stand-ins serve the same path, for service accounts only.

Port protocol. The back-end worker answers a subscription with {status, headers, stream: true}, then {chunk: <bytes>} per command, and {end: true} when the subscription stops. sw.js turns this into a ReadableStream response. In CPython the same endpoint is a FastAPI StreamingResponse.

Capture. The push is captured as server → <receiver> with K and push: true, at the moment it is written to the stream.

9.3 Authentication and permissions (FR-93, FR-97 to FR-102, FR-111 to FR-118)

Clients reach the data server directly (4.7, D-221). The stand-ins do what a stock OpenSensorHub with its security module on does, configured as below. Where that configuration is not yet proven, §14 says so.

  • Every request and every push subscription carries Authorization: Basic base64(user:password). Without valid credentials the answer is 401 (an HTML page) with WWW-Authenticate: basic, as OpenSensorHub sends it. The browser's native login dialog must never appear (FR-97): the display client always sends credentials, and the relay drops the WWW-Authenticate header on the way back. In a developed system the same is done by configuring OpenSensorHub or its web server (§14, D-226).
  • /profile.json also needs credentials.
  • Accounts, as the server's configuration (backend/barge/accounts.py and web/src/standin/accounts.ts; identical, and labelled demo credentials, PR-07):
Account Password Role / kind
owner demo-owner Owner
friend demo-friend Viewer (weather only)
analyst demo-analyst Viewer with emissions (for tests)
svc-importer, svc-data-cleanse, svc-summaries, svc-analysis svc-demo service: create and append only under their own systems (and the importer under the sensors' datastreams); read everything, CO₂ included
svc-new-model-1, svc-new-model-2 svc-demo service: as above, but no CO₂ unless the owner grants it (FR-113)
  • Permissions, per system. In OpenSensorHub a grant is inherited but a deny is not (S-AUTH), so restricting is done with an allow-list: each role is granted read on every open resource by id, and the list is extended as each import and each model creates datastreams (D-222). The stand-ins check by resource the same way:
    • read: every role reads every unrestricted system, plus its own workspace. Owner, Viewer with emissions, and the core service accounts also read restricted systems;
    • command: every user may send commands to the importer and every model's unrestricted control stream;
    • create and append: a user only under workspace:{self}; a service account only under its own systems. Stock OpenSensorHub meets this for top-level creation, but lets an account create subsystems under any system, and lets any account read another user's workspace (S-AUTH). Both are open (§14); the stand-ins refuse them, as the configured server is expected to.
  • A system the account may not read is listed, and refused (4.7, FR-93). It appears in /systems, /systems?searchMembers=true, /systems/{id}/subsystems, /datastreams, /systems/{id}/datastreams and /controlstreams, as OpenSensorHub lists it. Reading it, or anything under it (its datastreams' schemas, its observations, its control streams' commands), answers 403. The restricted systems are matched by unique id:
    • urn:x-barge:sensor:*:co2;
    • urn:x-barge:process:*:restricted;
    • other users' urn:x-barge:workspace:*.
  • The display client offers only what it can read (FR-118). At the handshake, a datastream whose schema answers 403 is left out of the field list, like a datastream it cannot use. It is not reported as missing, and it never makes a dataset degraded. The client has no list of restricted ids.
  • Role changes take effect on the next request (FR-116, D-151): the server reads the user-to-role assignment on every request. The admin stub (§13.5) changes it.
  • FR-112a. A pushed command carries sender, the user id. The receiving model looks that user's role up in the delivered assignment (accounts.py, accounts.ts), and rejects a command naming CO₂ if the role lacks emissions (D-152).
  • The importer and the core models in CPython and in the stand-in authenticate as their service accounts.

9.4 Redaction (FR-16a)

Every captured content replaces the value of Authorization with ****, and any JSON member named password with "****". The tap does this once, centrally, in tap.py and tap.ts. AT-53 searches every captured message for each demo password.

    async def command_status(self, cs_key, cmd_id, status, message="") -> None

Times are Unix seconds in every model (4.7): no simulation epoch.

A run is Run: its id, settings, start, end (exclusive), source (Data cleanse's run it reads), state (the model's own) and result. The runner calls step() again and again; the runner, not the model, subscribes, finds datasets, plans runs and logs them.

10.2 The runner (4.7: process on import)

Models follow no replay clock and no current dataset (FR-35, D-220). The runner:

  • Finds datasets by reading the importer's catalogue once per real second. Every dataset whose file status is imported, changed or superseded is one to process. Processing (this reading included) is counted, not drawn (D-283); a command and its status reports are drawn.
  • On a dataset not yet processed, it first declares every datastream the model may publish for it, restricted ones included, and runs__{ds}. It then processes the whole dataset, in whole windows [t0, t1) aligned to the dataset's start (D-129), oldest first, and the last, partial window at the dataset's end. Datasets are taken in the order they were imported.
  • Runs. A run id is <model>-<dataset id>-<n>. Run 1 is the first processing of a dataset. A settings command (§10.3) starts a new run of that model over every imported dataset, newest first. Analysis's clustering command starts one run on the dataset its doi names. Numbers carry on from the dataset's runs log, so they are never reused (after Reset instance the log is empty, and the next run is 1 again). The command reports ACCEPTED, then COMPLETED once its runs are queued, naming them (D-284); their progress is in runs__{ds}. Which runs a dataset needs is planned from its runs log: a model wants a complete run with its current settings; Analysis wants run 1 only (D-282).
  • Progress (FR-35b). Each run appends to runs__{ds}: time (real time), run_id, status (processing or complete), done_until (Time: the end of the last window done), pct (Count 0–100), and the settings it used. It appends a processing entry at the start and every 10 %, and a complete entry at the end. Analysis's runs also carry start, end, algorithm, resolution, records, clusters, score_changes and score_clusters (D-183).
  • Results. Every output observation carries its run_id. Nothing is replaced (FR-28a). A reader takes the latest complete run for the dataset (FR-35).
  • Determinism (AT-34). A run's outputs depend only on the dataset and the run's settings, never on when it ran, how long it took or what any client was doing.
  • Ready. A model publishes ready (its phase, for the shell) only after its subscription is open (AT-38).
  • After a server restart a model registers again and resubscribes. Datastreams and results persist across a restart, as in OpenSensorHub. A run cut short by the restart is restarted as a new run. The 4.6 restart hold (D-186) is withdrawn (D-228).
  • Order. Data cleanse reads weather__{ds} (and co2__{ds}). Every other model reads only Data cleanse's outputs (AT-15), and waits until Data cleanse's run on the dataset is complete. A run reads Data cleanse's latest complete run when it starts; it is not run again when Data cleanse runs again (D-282).
  • Windows (D-281). Data cleanse and Summaries take an hour at a time; Analysis a run's whole data range at once; the example new model an hour.
  • Speed (D-280). Data cleanse's blocks make a day a few hundred observations. Measured in Chromium: Mission A's three runs complete about 3 s after the flowchart in the stand-in and about 30 s after it in Python (each model first loads its own Pyodide).

11. Data of interest (FR-94 to FR-96a, FR-104 to FR-108)

The master is contracts/schemas/data-of-interest.json:

{ "version": 1, "label": "…", "note": "…",
  "dataset": {"file": "…", "size": 0, "modified": "…", "sha256": "…"},
  "start": "…Z", "end": "…Z", "resolution": "PT1S|PT1M|PT1H", "aggregation": "as-stored",
  "sources": [{"system": "urn:…", "output": "weather", "fields": ["air_temperature"]}],
  "run": "analysis-…-1", "created": {"at": "…Z", "by": "owner"} }
  • sources[].output is the output name without __{ds}. The dataset id is found again from dataset.sha256 when the record is opened, so a re-import restores it (FR-96).
  • Saving appends an observation to urn:x-barge:workspace:{user}|data-of-interest with fields time (save time), doi_id (Text), action (save or remove) and record (Text, the JSON). The list is folded from these.
  • On screen these are Favourites (SRD §8.5). The record's name stays "data of interest".
  • Resolution maps to datastreams: PT1S reads weather (Data cleanse's cleaned-* are blocks, for models, D-280); PT1M reads summary-1min-*; PT1H reads summary-1h-*. Analysis reads only Data cleanse's output (AT-15): at PT1M and PT1H it takes the means of its readings in intervals aligned to the dataset's start (D-288). Any other resolution is refused, naming these three (FR-94a).

13.2 Messages between the page and the back-end worker

The page sends:

  • start {folderUrl, ...};
  • connect, with a port for the relay;
  • model-connect {model};
  • control {action, arg}.

The worker posts:

  • progress {stage, detail, pct};
  • tick {messages, server} every 100 ms;
  • state {…};
  • relay-failed {…}.

The replay clock is the display client's, in the page (§8); no worker holds it.

13.3 Control actions

restart-server, down, up, field {name, on}, profile-lie, capture, reset-instance, set-role {user, role}, state. Each carries a request id, which the worker's answer echoes (D-167).

There is no play, pause, rate or freeze: replay is the display client's (§8), and Freeze is withdrawn.

13.5 Admin stub (FR-115)

The admin stub is the set-role {user, role} control action, offered in the control panel as "OpenSensorHub administration (stand-in)". It changes the delivered user-to-role assignment, which the server reads on the next request (§9.3).

13.6 URL parameters

?backend=python|standin, ?sketch=off and ?hand-made. ?seed is withdrawn: the data folder is fixed. For tests only, ?folder=<relative path>/ points the importer at another folder of the same site (D-272), and ?idle=<seconds> shortens the display client's 5-minute idle lock (D-305).

13.7 Startup and readiness (FR-125a, NFR-10a)

  • Steps. The loading progress names each step in turn: relay (registering the Service Worker and waiting until it controls the page), back end (the worker and, in Python mode, Pyodide), server (started and answering), import (the silent import of Mission A), models (each core model ready).
  • The relay. If a Service Worker already controls the page, it is used at once; the page does not wait for controllerchange. A new sw.js calls skipWaiting() and clients.claim(). If no Service Worker controls the page within 10 s, or registration fails (for example, the browser blocks Service Workers), the page says which step stalled and what to do (reload; allow the site's storage and Service Workers), rather than waiting silently (AT-68).
  • Any step that takes more than 10 s shows the same kind of message, naming the step.
  • Nothing plays after startup or Adopt until a user logs in, a dataset is open and Play is pressed.
  • Disabled controls say why (FR-125a), in a title and aria-describedby:
    • before startup completes: "Starting: ";
    • before login: "Log in to the display client first";
    • with no dataset open: "Open a dataset first".
