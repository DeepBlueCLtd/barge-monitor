# barge-monitor

A system and architecture demonstrator that runs whole in one browser tab (SRD Version 4.1,
on its way to 4.7 one phase at a time, `docs/plan-v4.7.md`):
an OGC API – Connected Systems server (OpenSensorHub, a stand-in here) whose CSV importer reads
a folder of awkward legacy CSV files, a self-configuring display client, and models that each run in their own worker and register
themselves over the same HTTP interface the display reads. Every component and every real
message is on screen, and the company's value-add (the display client and the models) is
marked. The opening panel lists what is adopted rather than designed, what is written for
this system, and what a developed system needs that is not here. **Failure demos** in the
top bar take the server down, remove a source, misconfigure the server, lock the screen, import
an overlapping file or log in as a friend without CO₂, and say what to watch for.

**Demonstrator:** https://deepbluecltd.github.io/barge-monitor/demo/ ·
**Requirements:** https://deepbluecltd.github.io/barge-monitor/

Everything is fictional: the canal, its places and the weather.

**Where the 4.7 work stands.** Phases 1 to 6 are in: the 4.7 masters and the server-neutral
contract suite; the CSV data folder; a robust startup; the data
server, in both back ends, behaving as a configured stock OpenSensorHub
(`docs/v4-interfaces.md` §9): Basic credentials on every request (labelled demo accounts:
`owner`/`demo-owner`, `friend`/`demo-friend`, `analyst`/`demo-analyst`, service accounts
`svc-*`/`svc-demo`), restricted CO₂ resources listed and refused with 403, opaque identifiers,
discovery by `searchMembers`, one observation per `POST`, `405` for `PUT` and `DELETE`, and
commands pushed to receivers subscribed on `/api-internal`; and the **CSV importer**, a module of
the server in both back ends (`docs/v4-interfaces.md` §7): an archive `catalogue` of the folder,
an `import` control stream (`import`, `rescan`), bulk writes into per-dataset datastreams under the
sensors and the CO₂ analysers, QC on import, change and supersede detection, the silent import of
Mission A at every page load, and Reset instance in the control panel; and the **models on
import** (`docs/v4-interfaces.md` §10.2): Data cleanse, Summaries and Analysis process each
imported dataset whole, in windows aligned to its start, log each run's progress in
`runs__{dataset}`, start a new run on a settings command, and publish anything derived from CO₂
under restricted subsystems; and the **4.7 display client** (SRD §8, plan Phase 7): login and lock,
the handshake against the template profile, the Dataset selector and Favourites popups, its own
replay clock that reads only up to its replay time, "results being prepared" from the runs logs,
and sources the server refuses (403) left out generically; and the **4.7 shell** (SRD §9, plan
Phase 8): the six components in four zones with every flow of §3.1 drawn and labelled "HTTP",
"push" or "inside the server", the god's-eye note, detail panels for every component (the data
folder, the CSV importer, the data server, Models with outputs and runs per dataset), the
control panel and every failure demo of FR-79a. The top bar's **Pause system** freezes the whole
system for inspection (icons stay put and clickable, nothing is sent, Resume loses nothing), with a
slow-motion drawing speed (½×, ¼×) beside it (D-362); replay is the display client's own. The 4.1
world run, history, logger, store adapter and simulation clock are retired (D-320): the data
folder is the only data. And the **adoption opening** (SRD §9.8, plan Phase 9): with `?hand-made`
the demonstrator opens on the data server as we would write it ourselves, a range of subsystem
components to develop drawn as the equals of the CSV importer and Models, in two rows of five;
nothing runs until *Open Standards* (a short history of OGC API – Connected Systems and a tree of
its entities, D-363) and then *OpenSensorHub*, which starts the back end and merges them, one at a time,
into the one Data server card, then hands over to the normal layout; the flowchart stays on screen
while the back end finishes starting (D-360).

## Run it locally

```sh
pip install -r backend/requirements-dev.txt
(cd backend && python -m pytest -q)                      # Python tests (the stand-in's half needs web/node_modules)

python scripts/build_data_folder.py && python scripts/build_data_folder.py --check   # web/public/data/folder
cd web
npm ci
npm run pyodide          # Pyodide 0.29.5 and packages into ../.cache (once)
node scripts/standin-check.mjs   # the 4.7 contract against the stand-in in Node
npm run build            # generates TypeScript types from contracts/, packs the Python
npm run site             # assembles ../dist-site/{demo,pyodide}
npm run serve            # http://localhost:8080/demo/
npm run e2e              # Playwright tests (E2E_PORT, default 8080, and the next port for
                         # the site under /barge-monitor/pr/17/, as a preview is published)
```

`?backend=python` runs the Python back end and models in Pyodide; `?backend=standin` the
JavaScript stand-in; `?sketch=off` draws plain outlines; `?hand-made` opens on the adoption
opening (SRD §9.8); `?folder=<relative path>/` points the importer at another folder of the same
site (for tests, D-272).

## Current state

| What | Now | Why, and how to change it |
|---|---|---|
| Default back end | the JavaScript stand-in (about 3 s to the flowchart) | It starts quickly. `?backend=python` runs Python in Pyodide (about 30 s to the first charts). `PYTHON_BY_DEFAULT = true` in `web/src/shell/runtime.ts` makes Python the default wherever WebAssembly runs; the browser tests name their back end, so nothing else changes |
| Importing | Mission A silently at every page load; the others on an `import` command | A command over HTTP: `POST api/controlstreams/{import}/commands` with `{"parameters": {"action": "import", "file": "MISSION_C_20310421.csv"}}`. The data folder's and the CSV importer's panels show the folder and the last import's rows/s; the control panel has Reset instance. The display client's Dataset selector sends it, with progress on its button |
| Models | every imported dataset, whole, on import | Mission A's three runs complete about 3 s after the flowchart in the stand-in and about 24 s after it in Python (each model loads its own Pyodide first; D-342); a 12-hour dataset takes about 2 s and 15 s. Data cleanse publishes its output in hourly blocks (D-280): one observation per `POST` (§9.1) makes a reading per observation too slow. A settings command (`POST api/controlstreams/{settings}/commands`) starts a new run over every dataset |
| Startup budgets (NFR-10, D-340, D-350) | 30 s to every core model ready (registered and subscribed; Mission A is processed after, "results being prepared"); a cold start downloads at most 5 MB (stand-in) and 100 MB (Python); the data folder at most 8 MB (`web/src/budgets.ts`) | Measured in both back ends by `web/e2e/hardening.spec.ts`: about 1 s and 3.3 MB in the stand-in; 9 to 10 s (Mission A processed at about 25 s) and up to 91 MB in Python on a 4-core machine |
| The display client | after login, Mission A open and paused | Its own replay clock (0.1× to 100×); the demo accounts on its login screen; `?idle=<seconds>` shortens the 5-minute lock, for tests only (D-305) |

With the stand-in, the empty-slot model editor (Python) is unavailable; the Models panel
offers a link that reloads with `?backend=python`.

The server also runs under an ordinary ASGI server, with the core models in-process:
`cd backend && python -c "import uvicorn; from barge.runtime import Runtime; from barge.api import create_app; rt = Runtime(pregen_days=1, local_models=True); [rt.tick() for _ in range(200)]; uvicorn.run(create_app(rt))"`.
